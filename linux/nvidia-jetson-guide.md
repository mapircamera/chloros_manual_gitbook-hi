## जेटसन पर डायनामिक कम्प्यूट एडैप्शन

### यह कैसे काम करता है

स्टार्टअप पर,Chloros

आपके सिस्टम का प्रोफाइल बनाता है:

1. **`/proc/device-tree/model` के माध्यम से जेटसन मॉडल का पता लगाता है**

2.**उपलब्ध साझा GPU/CPU मेमोरी पढ़ता है** (जेटसन एकीकृत मेमोरी का उपयोग करता है)
3. **एक प्रोसेसिंग रणनीति चुनता है** (`GPU_PARALLEL`, `GPU_SINGLE`, या `CPU_PARALLEL`)
4. **वर्कर काउंट, पाइपलाइन टाइप, और मेमोरी आवंटन सेट करता है** स्वचालित रूप से

यह निर्णय मॉडल के नाम से नहीं, बल्कि **कुल साझा रैम** से संचालित होता है:

* **12GB से कम कुल रैम**(सभी 8GB जेटसन्स):**1 वर्कर के साथ `GPU_SINGLE` — जानबूझकर क्रमिक प्रसंस्करण**। समांतर वर्कर्स के लिए मेमोरी बहुत कम है, इसलिए छवियों को एक बार में एक करके संसाधित किया जाता है।**8GB या उससे कम** वाले Jetsons पर, थ्रेड 3 वर्कर पूल को पूरी तरह से छोड़ देता है और अपनी प्रति-छवि कार्य को इन-प्रोसेस चलाता है।
* **12GB या उससे अधिक**(Orin NX 16GB, AGX Orin): एकीकृत मेमोरी `GPU_PARALLEL` के लिए योग्य है, लेकिन**जेत्सन पर वर्कर की संख्या 2 पर सीमित** है — GPU, वर्कर प्रक्रियाओं की RAM, और उनके प्रति-वर्कर CUDA संदर्भ सभी एक ही साझा पूल से मेमोरी लेते हैं, इसलिए अधिक वर्कर होने पर मेमोरी की कमी के कारण विफलता का खतरा रहता है।

आप `CHLOROS_STRATEGY` पर्यावरण चर के साथ स्वचालित विकल्प को ओवरराइड कर सकते हैं — [डायनामिक कम्प्यूट एडैप्शन](../processing-architecture/dynamic-compute-adaptation.md#manual-strategy-override) देखें।

### प्रति-मॉडल व्यवहार

| जेटसन मॉडल                | रणनीति       | वर्कर्स | निष्पादन                                      |
| --------------------------- | -------------- | ------- | ---------------------------------------------- |
| **Jetson Orin Nano 8GB**    | `GPU_SINGLE`   | 1       | क्रमिक इन-प्रोसेस लूप (मेमोरी दबाव के तहत `tiled_gpu`) |
| **जेसन ओरिन एनएक्स 8GB**      | `GPU_SINGLE`   | 1       | क्रमिक इन-प्रोसेस लूप                     |
| **जेसन ओरिन NX 16GB**     | `GPU_PARALLEL` | 2       | समानांतर वर्कर प्रक्रियाएं, `fused_gpu` पथ  |
| **जेसन एजीएक्स ओरिन 32-64GB** | `GPU_PARALLEL` | 2       | समानांतर वर्कर प्रक्रियाएं, `fused_gpu` पथ  |

प्लेटफ़ॉर्म के बीच मुख्य अंतर **मेमोरी** है। जब दबाव अधिक होता है, तो 8GB वाले जेटसन को मेमोरी-कुशल टाइल वाले दृष्टिकोण का उपयोग करके एक समय में एक छवि को प्रोसेस करना होता है, जबकि 16GB+ वाला ओरिन उच्च-थ्रूपुट वाले फ्यूज्ड पाइपलाइन का उपयोग करके एक साथ GPU के माध्यम से 2 छवियों को चला सकता है।

### प्रति-मॉडल जीपीयू बजट

प्रत्येक जेटसन मॉडल में एक हार्डवेयर प्रोफ़ाइल भी होती है जो यह सीमा निर्धारित करती है कि साझा पूल में से प्रोसेसिंग कितनी मांग सकती है, और बैच साइज़ को स्केल करती है:

| मॉडल | जीपीयू बजट सीमा | बैच-साइज़ गुणक | सिस्टम/डिस्प्ले के लिए आरक्षित |
| --- | --- | --- | --- |
| **जेत्सन ओरिन नैनो** | 70% | ×0.8 | 2.0 जीबी |
| **जेत्सन ओरिन एनएक्स** | 75% | ×1.0 | 3.0 जीबी |
| **जेत्सन एजीएक्स ओरिन**| 80% | ×1.5 | 4.0 जीबी |

डिटेक्टेड रैम प्रोफ़ाइल को समायोजित करती है:**16GB या उससे अधिक** रिपोर्ट करने वाले जेत्सन का बैच गुणक ×1.2 से बढ़ा दिया जाता है। गुणकों से पहले बेस बैच साइज़ 8 इमेज है।

पूर्ण कम्प्यूट अनुकूलन संदर्भ के लिए, [डायनामिक कम्प्यूट अनुकूलन](../processing-architecture/dynamic-compute-adaptation.md) देखें।

## नैनो और ओरिन नैनो पर टेक्सचर अवेयर के लिए जीपीयू फ़्रीक्वेंसी कैप

टेक्सचर अवेयर डेबायर GPU न्यूरल-नेटवर्क इंफरेंस चलाता है, जो पूरी GPU क्लॉक स्पीड पर कम-पावर वाले जेटसन मॉडल (10-15W क्लास) पर **ओवर-करंट चेतावनियाँ**ट्रिगर कर सकता है।**Jetson Nano या Orin Nano** पर Texture Aware प्रोसेसिंग से पहले,Chloros

GPU की अधिकतम फ़्रीक्वेंसी की जाँच करता है और यदि यह वर्तमान में उच्च है तो इसे **510 MHz** (510000000) तक सीमित कर देता है:

* यदिCLI

GPU आवृत्ति sysfs नोड में लिख सकता है, तो कैप **स्वचालित रूप से लागू हो जाता है** और एक पुष्टि प्रिंट की जाती है।
* यदि नहीं (रूट की आवश्यकता है), तो  कैप को मैन्युअल रूप से लागू करने के लिए सटीक `sudo` कमांड प्रिंट करता है, थोड़ी देर प्रतीक्षा करता है ताकि आप इसे पढ़ सकें, फिर जारी रखता है — प्रोसेसिंग अभी भी चलती है लेकिन ओवर-करंट चेतावनियाँ दिखा सकती हैं।

प्रोसेसिंग से पहले स्वयं कैप लागू करने के लिए:

```bash
echo 510000000 | sudo tee /sys/devices/platform/bus@0/17000000.gpu/devfreq/17000000.gpu/max_freq
```

अधिक-पावर वाले मॉडल (Orin NX 25W, AGX Orin 60W) पूरी GPU गति पर चलते हैं; कोई कैप लागू नहीं किया जाता है। स्टैंडर्ड डेबायर किसी भी मॉडल पर कैप को कभी भी ट्रिगर नहीं करता है।

{% hint style="info" %}
**जेक्सन पर टेक्सचर अवेयर हमेशा एक समय में एक इमेज पर चलता है।** प्रत्येक वर्कर को अपने CUDA कॉन्टेक्स्ट (~1GB) और डिनॉइज़र मॉडल की अपनी कॉपी की आवश्यकता होगी, जिसे यूनिफाइड मेमोरी वहन नहीं कर सकती — इसलिए जेक्सन पर टेक्सचर अवेयर पाथ को एक सिंगल वर्कर पर पिन किया जाता है और GPU एक्सेस को सीरियलाइज़ किया जाता है। किसी भी Jetson पर Texture Aware के Standard की तुलना में काफी धीमा होने की उम्मीद करें।
{% endhint %}

## थर्मल प्रबंधन

जेत्सन डिवाइसों में सीमित थर्मल हेडरूम होता है, खासकर बंद या हवा में तैरने वाले डिप्लॉयमेंट्स में।Chloros

SoC तापमान की निगरानी करता है और स्वचालित रूप से बैच साइज़ को थ्रॉटल करता है:

| तापमान         | कार्रवाई                                            |
| ------------------- | ------------------------------------------------- |
| **&lt; 70°C**          | सामान्य संचालन — पूर्ण प्रसंस्करण गति          |
| **70°C** (चेतावनी)  | बैच आकार क्रमिक रूप से कम हो जाता है (70°C और 80°C के बीच 100% → 50%) |
| **80°C** (गंभीर) | आक्रामक थ्रॉटलिंग (80°C और 90°C के बीच 50% → 0%) |
| **90°C** (शटडाउन) | जीपीयू प्रोसेसिंग पूरी तरह से बंद — ठंडा होने की आवश्यकता |

{% hint style="warning" %}
**सतत प्रोसेसिंग के लिए पर्याप्त वेंटिलेशन और हीट सिंकिंग सुनिश्चित करें**, विशेष रूप से बंद फील्ड एनक्लोजर या एयरबोर्न सिस्टम में। थर्मल थ्रॉटलिंग हार्डवेयर की सुरक्षा के लिए प्रोसेसिंग थ्रूपुट को कम कर देगी।
{% endhint %}

## मेमोरी प्रबंधन

जेत्सन डिवाइस **एकीकृत मेमोरी** का उपयोग करते हैं — GPU और CPU एक ही भौतिक RAM साझा करते हैं। रिपोर्ट की गई VRAM (जैसे Orin NX 16GB पर ~15.3GB) समर्पित GPU मेमोरी नहीं है; यह वही RAM है जिसका उपयोग ऑपरेटिंग सिस्टम और हर दूसरी प्रक्रिया कर रही है।

### स्वैप चेतावनी और सिफ़ारिशें

Jetson पर प्रोसेसिंग से पहले, CLI आपके इनपुट फ़ोल्डर में रॉ (RAW) इमेज की गिनती करता है (`.tif`, `.tiff`, `.raw`, `.dng` — JPG पूर्वावलोकन की गिनती नहीं की जाती है), रन के लिए आवश्यक पीक मेमोरी का अनुमान लगाता है, और यदि रैम + स्वैप अपर्याप्त होने की संभावना है तो **शुरू करने से पहले चेतावनी देता है**। चेतावनी का शीर्षक `LOW MEMORY WARNING - Jetson Detected` है, यह आपकी छवियों की गिनती प्रिंट करता है, RAM, वर्तमान स्वैप, और अनुमानित पीक, फिर सटीक `fallocate` / `chmod` / `mkswap` / `swapon` कमांड्स आपके प्रोजेक्ट के लिए आकार के होते हैं (कभी भी 8GB से छोटे नहीं)। यह कुछ सेकंड के लिए रुकता है ताकि संदेश स्क्रॉलबैक में खो न जाए, फिर प्रोसेसिंग जारी रहती है।**चेतावनी द्वारा उपयोग किए जाने वाले मेमोरी अनुमान:**

| डेबायर मोड | बेस | प्रति छवि |
| --- | --- | --- |
| स्टैंडर्ड | ~1.5 GB | ~10 MB |
| टेक्सचर अवेयर | ~2.5 GB (मॉडल + पाइथन रनटाइम) | ~15 MB |

यह चेतावनी तब आती है जब अनुमानित पीक, रैम + स्वैप में से 1GB की सुरक्षा मार्जिन से अधिक हो जाता है, और यह केवल **फ़ाइल-समर्थित** स्वैप की ही गिनती करती है — एक ज़राम-ओनली सेटअप को फिर भी फ़्लैग किया जाएगा।

मैन्युअल रूप से स्वैप जोड़ने के लिए (उदाहरण: 8GB):

```bash
# Check current memory and swap
free -h

# Create a swap file
sudo fallocate -l 8G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile

# Make persistent across reboots
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

### OOM (आउट ऑफ मेमोरी) हैंडलिंग

प्रोसेसिंग के दौरान,Chloros

जीपीयू मेमोरी की निगरानी करता है और क्रैश होने के बजाय सुचारू रूप से प्रदर्शन क्षमता कम कर देता है:

1. जब GPU मेमोरी का उपयोग **85%** से अधिक हो जाता है, तो बैच साइज़ को पूर्व-सचेत रूप से कम कर दिया जाता है
2. यदि फिर भी कोई आउट-ऑफ-मेमोरी घटना होती है, तो बैच साइज़ को **आधा** कर दिया जाता है, और प्रत्येक लगातार OOM पर फिर से आधा कर दिया जाता है; प्रत्येक बाद का सफल बैच उस पेनल्टी को एक कदम पीछे ले जाता है
3. निरंतर दबाव में, पाइपलाइन `fused_gpu` से मेमोरी-कुशल `tiled_gpu` पथ पर, और अंतिम उपाय के रूप में सीपीयू प्रसंस्करण पर वापस चली जाती है

### स्टोरेज सिफ़ारिशें

* arm64 डिप्लॉयमेंट्स के लिए **NVMe SSD** की पुरज़ोर सिफ़ारिश की जाती है
* SD कार्ड प्रोसेसिंग के लिए बहुत धीमे होते हैं — केवल बूट मीडिया के रूप में उपयोग करें
* संसाधित आउटपुट के लिए अपने कच्चे छवि डेटा आकार का 2-3 गुना योजना बनाएँ

### LATTICE / DAQ-E टाइम सिंक के लिए ऑलवेज-ऑन बैकएंड

यदि आपका Jetson हेडलेस रूप से LATTICE कैमरों या DAQ-E लाइट सेंसरों को नियंत्रित करता है, तो बैकएंड systemd सेवा को सक्षम करें ताकि PTP ग्रैंडमास्टर लगातार चले (यह यूनिट डिफ़ॉल्ट रूप से इंस्टॉल तो होती है लेकिन सक्षम नहीं होती है):

```bash
sudo systemctl enable --now chloros-backend.service
chloros-cli time-sync status
```

विवरण के लिए [Linux

इंस्टॉलेशन](linux-installation.md#always-on-ptp-for-headless-hosts) देखें, जिसमें यह भी शामिल है कि यह पैकेज रूट के बिना PTP पोर्ट 319/320 को बाइंड करने योग्य कैसे बनाता है।

### systemd के साथ स्वचालित प्रसंस्करण

स्वचालित प्रसंस्करण के लिए एक systemd सेवा बनाएँ:

```ini
# /etc/systemd/system/chloros-process.service
[Unit]
Description=Chloros Automated Processing
After=network.target

[Service]
Type=oneshot
User=chloros
ExecStart=/usr/bin/chloros-cli process /data/incoming --output /data/processed
StandardOutput=append:/var/log/chloros-process.log
StandardError=append:/var/log/chloros-process.log

[Install]
WantedBy=multi-user.target
```

जब कोई रन जो उत्पादों का अनुरोध करता है, कोई छवि नहीं लिखता है तो `chloros-cli process` शून्य-से-अधिक मान पर बाहर निकलता है, इसलिए systemd की विफलता स्थिति निगरानी के लिए सार्थक है।

निर्धारित प्रसंस्करण के लिए एक systemd टाइमर के साथ पेयर करें:

```ini
# /etc/systemd/system/chloros-process.timer
[Unit]
Description=Run Chloros Processing Every Hour

[Timer]
OnCalendar=hourly
Persistent=true

[Install]
WantedBy=timers.target
```

```bash
sudo systemctl enable chloros-process.timer
sudo systemctl start chloros-process.timer
```

## उदाहरण वर्कफ़्लो

### बुनियादी जेटसन प्रोसेसिंग

```bash
#!/bin/bash
# Process a drone flight dataset on Jetson
chloros-cli process /data/flights/flight_042 \
    --output /data/processed/flight_042 \
    --format "TIFF (32-bit, Percent)" \
    --indices NDVI NDRE GNDVI
```

### जेटसन परPython

SDK



```python
from chloros_sdk import ChlorosLocal

with ChlorosLocal() as chloros:
    chloros.create_project("field_survey_042")
    chloros.import_images("/data/flights/flight_042")
    chloros.configure(
        indices=["NDVI", "NDRE", "GNDVI"],
        export_format="TIFF (32-bit, Percent)",
        reflectance_calibration=True
    )
    chloros.process(mode="parallel")

print("Processing complete!")
```

### एकाधिक उड़ानों की बैच प्रोसेसिंग

```bash
#!/bin/bash
# Process all flight datasets in a directory
for flight in /data/flights/*/; do
    name=$(basename "$flight")
    echo "Processing $name..."
    chloros-cli process "$flight" \
        --output "/data/processed/$name" \
        --format "TIFF (32-bit, Percent)" \
        --indices NDVI NDRE
    echo "Completed $name"
done
```
