# NVIDIA Jetson गाइड NVIDIA Jetson पर

Chloros एज पर मल्टीस्पेक्ट्रल इमेज प्रोसेसिंग को सक्षम करता है — फील्ड में, UAVs पर, और रिमोट इंस्टॉलेशन में। Chloros 1.3.0 स्टार्टअप पर आपके Jetson मॉडल का पता लगाता है और पाए गए हार्डवेयर के लिए इसकी प्रोसेसिंग रणनीति को अनुकूलित करता है। **कोई मैन्युअल ट्यूनिंग आवश्यक नहीं है।**
{% hint style="info" %}
**

1.3.0 Jetson पैकेज Jetson के GPU पर प्रोसेस करता है।** `chloros_1.3.0_arm64_jp6.deb` को JetPack 6 के लिए बनाया गया है और यह JetPack 6 के PyTorch के CUDA बिल्ड का उपयोग करता है, इसलिए प्रोसेसिंग, जिसमें Texture Aware debayer भी शामिल है, Orin के GPU पर चलती है। यह पैकेज स्वयं CUDA को शामिल नहीं करता है: यह उन CUDA और cuDNN लाइब्रेरियों का उपयोग करता है जिन्हें JetPack 6 इंस्टॉल करता है (उन छवियों पर `sudo apt install nvidia-jetpack` जिनमें वे मौजूद नहीं हैं)। जहाँ कोई CUDA GPU उपयोगी नहीं है, वहाँ प्रोसेसिंग CPU पर चलती है और Texture Aware स्टैंडर्ड debayer का उपयोग करता है।
{% endhint %}

## आवश्यकताएँ

* **JetPack 6.x** (नवीनतम की सिफारिश की जाती है)
* JetPack 6 से **NVIDIA CUDA और cuDNN** (यदि आपकी इमेज में ये नहीं हैं तो `sudo apt install nvidia-jetpack`)
* **पेड Chloros+ प्लान** — कॉपर टियर या उच्चतर (सभी CLI/SDK एक्सेस के लिए आवश्यक; सर्वर-साइड पर लागू)

## स्थापना

```bash
# Install the arm64 .deb package (JetPack 6) -- apt, not dpkg -i, so the
# Python SDK's requirements (python3-numpy, python3-requests) come too
sudo apt install ./chloros_1.3.0_arm64_jp6.deb

# Verify installation
chloros-cli --version    # prints "Chloros CLI 1.3.0"
python3 -c "import chloros_sdk; print(chloros_sdk.__version__)"   # the .deb installs the SDK

# Run system diagnostics
chloros-cli selftest
```

`.deb`, `python3` सिस्टम के लिए Python SDK स्थापित करता है, जो इस बिल्ड से मेल खाता है। केवल एक वर्चुअलएन्वायरन को बंडल किए गए व्हील को इसमें इंस्टॉल करने की आवश्यकता होती है: `pip install /usr/lib/chloros/sdk/chloros_sdk-*.whl` (पूरी तरह से ऑफ़लाइन)। सामान्य Linux इंस्टॉलेशन विवरण, फ़ाइल स्थानों और समस्या निवारण के लिए, [Linux इंस्टॉलेशन](linux-installation.md) देखें।

{% hint style="info" %}
**लॉन्च करते समय अब और अनपैकिंग नहीं होगी।**

1.3.0 से, बैकएंड और CLI, `/usr/lib/chloros/` के तहत अनपैक होकर इंस्टॉल होते हैं, इसलिए वे अब हर बार शुरू होने पर खुद को एक अस्थायी डायरेक्टरी में एक्सट्रेक्ट नहीं करते हैं। अस्थायी फ़ाइलें तब भी स्वचालित रूप से `/mnt/ssd/tmp` में जाती हैं जब वह फ़ोल्डर मौजूद होता है; अन्यथा आप `TMPDIR` को अपने NVMe (`export TMPDIR=/mnt/nvme/tmp`) पर एक पथ पर सेट कर सकते हैं।
{% endhint %}

## जेटसन पर डायनामिक कम्प्यूट एडैप्शन

### यह कैसे काम करता है

स्टार्टअप पर, Chloros आपके सिस्टम का प्रोफाइल करता है:

1. **`/proc/device-tree/model`**के माध्यम से**जेत्सन मॉडल का पता लगाता है**

2.**उपलब्ध साझा GPU/CPU मेमोरी पढ़ता है** (Jetson एकीकृत मेमोरी का उपयोग करता है)
3. **PyTorch से पूछता है कि क्या यह CUDA का उपयोग कर सकता है** — JetPack 6 के CUDA और cuDNN इंस्टॉल होने पर, यह कर सकता है
4. **एक प्रोसेसिंग रणनीति चुनता है** (`GPU_PARALLEL`, `GPU_SINGLE`, या `CPU_PARALLEL`) और वर्कर की संख्या स्वचालित रूप से

यह निर्णय मॉडल के नाम से नहीं, बल्कि **कुल साझा रैम** से संचालित होता है:

* **12GB से कम कुल रैम**(सभी 8GB जेटसन्स):**1 वर्कर — जानबूझकर क्रमिक प्रसंस्करण**। एक साथ चलने वाले वर्कर्स के लिए मेमोरी बहुत कम है, इसलिए छवियों को एक-एक करके संसाधित किया जाता है।**8GB या उससे कम** वाले जेटसन्स पर, थ्रेड 3 वर्कर पूल को पूरी तरह से छोड़ देता है और अपनी प्रति-छवि का काम इन-प्रोसेस चलाता है। बैकएंड लॉग इस रणनीति को `GPU_SINGLE` नाम देता है।
* **12GB या उससे अधिक**(Orin NX 16GB, AGX Orin): एकीकृत मेमोरी `GPU_PARALLEL` के लिए योग्य है, लेकिन**जेसन पर वर्कर की संख्या 2 पर सीमित है** — GPU, वर्कर प्रक्रियाओं की RAM, और उनके प्रति-वर्कर CUDA संदर्भ सभी एक ही साझा पूल से मेमोरी लेते हैं, इसलिए अधिक वर्कर्स के साथ मेमोरी खत्म होने की विफलता का खतरा रहता है।
* **उपयोगी CUDA नहीं** (JetPack की CUDA लाइब्रेरीज़ अनुपस्थित): 12GB या उससे अधिक पर `CPU_PARALLEL`, और उससे कम पर एक समय में एक इमेज।

आप `CHLOROS_STRATEGY` पर्यावरण चर के साथ स्वचालित विकल्प को ओवरराइड कर सकते हैं — [डायनामिक कम्प्यूट एडैप्शन](../processing-architecture/dynamic-compute-adaptation.md#manual-strategy-override) देखें।

### प्रति-मॉडल व्यवहार

| जेटसन मॉडल                | रणनीति       | वर्कर्स | निष्पादन                                      |
| --------------------------- | -------------- | ------- | ---------------------------------------------- |
| **जेसन ओरिन नैनो 8GB**    | `GPU_SINGLE`   | 1       | क्रमिक इन-प्रोसेस लूप (मेमोरी दबाव के तहत `tiled_gpu`) |
| **जेसन ओरिन NX 8GB**      | `GPU_SINGLE`   | 1       | क्रमिक इन-प्रोसेस लूप                     |
| **जेसन ओरिन NX 16GB**     | `GPU_PARALLEL` | 2       | समानांतर वर्कर प्रक्रियाएं, `fused_gpu` पथ  |
| **जेसन एजीएक्स ओरिन 32-64GB** | `GPU_PARALLEL` | 2       | समानांतर वर्कर प्रक्रियाएं, `fused_gpu` पथ  |

प्लेटफ़ॉर्म के बीच मुख्य अंतर **मेमोरी** है। जब दबाव अधिक होता है, तो 8GB वाले जेटसन को मेमोरी-कुशल टाइल वाले दृष्टिकोण का उपयोग करके एक बार में एक छवि को प्रोसेस करना होता है, जबकि 16GB+ वाला ओरिन उच्च-थ्रूपुट वाले फ्यूज्ड पाइपलाइन का उपयोग करके एक साथ GPU के माध्यम से 2 छवियों को चला सकता है।

### प्रति-मॉडल जीपीयू बजट

प्रत्येक जेटसन मॉडल में एक हार्डवेयर प्रोफ़ाइल भी होती है जो यह सीमा निर्धारित करती है कि साझा पूल से कितनी प्रोसेसिंग का दावा किया जा सकता है, और बैच साइज़ को स्केल करती है:

| मॉडल | जीपीयू बजट सीमा | बैच-साइज़ गुणक | सिस्टम/डिस्प्ले के लिए आरक्षित |
| --- | --- | --- | --- |
| **जेत्सन ओरिन नैनो** | 70% | ×0.8 | 2.0 जीबी |
| **जेत्सन ओरिन एनएक्स** | 75% | ×1.0 | 3.0 जीबी |
| **जेसन एजीएक्स ओरिन**| 80% | ×1.5 | 4.0 जीबी |

डिटेक्टेड रैम प्रोफ़ाइल को समायोजित करती है:**16GB या उससे अधिक** रिपोर्ट करने वाले एक जेसन का बैच मल्टीप्लायर ×1.2 से बढ़ा दिया जाता है। मल्टीप्लायर से पहले बेस बैच साइज़ 8 इमेज है।

पूर्ण कम्प्यूट अनुकूलन संदर्भ के लिए, [डायनामिक कम्प्यूट अनुकूलन](../processing-architecture/dynamic-compute-adaptation.md) देखें।

## नैनो और ओरिन नैनो पर टेक्सचर अवेयर के लिए जीपीयू फ़्रीक्वेंसी कैप

टेक्सचर अवेयर डेबायर GPU न्यूरल-नेटवर्क इंफरेंस चलाता है, जो कम-पावर वाले जेटसन मॉडलों (10-15W क्लास) पर पूरी GPU क्लॉक स्पीड पर **ओवर-करंट चेतावनियाँ**ट्रिगर कर सकता है। जब आप `--debayer texture-aware` को**जेसन नैनो या ओरिन नैनो** पर, CLI GPU की अधिकतम आवृत्ति की जाँच करता है और यदि यह वर्तमान में उच्च है तो इसे **510 MHz** (510000000) तक सीमित कर देता है:

* यदि CLI GPU आवृत्ति sysfs नोड में लिख सकता है, तो कैप **स्वचालित रूप से लागू हो जाता है** और एक पुष्टिकरण प्रिंट किया जाता है।
* यदि नहीं (रूट की आवश्यकता है), तो CLI कैप को मैन्युअल रूप से लागू करने के लिए सटीक `sudo` कमांड प्रिंट करता है, थोड़ी देर प्रतीक्षा करता है ताकि आप इसे पढ़ सकें, फिर जारी रखता है — प्रोसेसिंग अभी भी चलती है लेकिन ओवर-करंट चेतावनियाँ दिखाई दे सकती हैं।

प्रोसेसिंग से पहले कैप स्वयं लागू करने के लिए:

```bash
echo 510000000 | sudo tee /sys/devices/platform/bus@0/17000000.gpu/devfreq/17000000.gpu/max_freq
```

अधिक-पावर वाले मॉडल (Orin NX 25W, AGX Orin 60W) पूरी GPU गति पर चलते हैं; कोई कैप लागू नहीं होता है। स्टैंडर्ड डेबायर किसी भी मॉडल पर कैप को कभी भी ट्रिगर नहीं करता है।

{% hint style="info" %}
**Jetson पर टेक्सचर अवेयर हमेशा एक समय में एक छवि पर चलता है।** प्रत्येक वर्कर को अपने स्वयं के CUDA संदर्भ (~1GB) और डिनॉइज़र मॉडल की अपनी प्रतिलिपि की आवश्यकता होगी, जिसे यूनिफाइड मेमोरी वहन नहीं कर सकती — इसलिए Jetson पर टेक्सचर अवेयर पथ को एकल वर्कर पर पिन किया जाता है और GPU एक्सेस को सीरियलाइज़ किया जाता है। किसी भी Jetson पर टेक्सचर अवेयर के स्टैंडर्ड की तुलना में काफी धीमा होने की उम्मीद करें। टेक्सचर अवेयर Survey3 इमेज पर लागू होता है: LATTICE कैप्चर हमेशा स्टैंडर्ड डेबेयर का उपयोग करते हैं। उपयोग योग्य CUDA GPU के बिना, रन स्टैंडर्ड का उपयोग करता है, और बैकएंड यह बताने वाली एक `[DEBAYER] … needs a CUDA GPU …` लाइन लॉग करता है (`chloros-cli --verbose` के साथ दिखाया गया है)।
{% endhint %}

## थर्मल प्रबंधन

जेत्सन डिवाइसों में सीमित थर्मल हेडरूम होता है, खासकर बंद या हवा में तैरते हुए डिप्लॉयमेंट में। Chloros SoC तापमान की निगरानी करता है और बैच साइज़ को स्वचालित रूप से थ्रॉटल करता है:

| तापमान         | कार्रवाई                                            |
| ------------------- | ------------------------------------------------- |
| **< 70°C**          | सामान्य संचालन — पूरी प्रोसेसिंग गति          |
| **70°C** (चेतावनी) | बैच का आकार क्रमिक रूप से कम होता है (70°C और 80°C के बीच 100% → 50%) |
| **80°C** (गंभीर) | आक्रामक थ्रॉटलिंग (80°C और 90°C के बीच 50% → 0%) |
| **90°C** (शटडाउन) | जीपीयू प्रोसेसिंग पूरी तरह से बंद — ठंडा करने की आवश्यकता |

{% hint style="warning" %}
**सतत प्रोसेसिंग के लिए पर्याप्त वेंटिलेशन और हीट सिंकिंग सुनिश्चित करें**, विशेष रूप से बंद फील्ड एनक्लोजर या हवाई प्रणालियों में। थर्मल थ्रॉटलिंग हार्डवेयर की सुरक्षा के लिए प्रोसेसिंग थ्रूपुट को कम कर देगी।
{% endhint %}

## मेमोरी प्रबंधन

जेत्सन डिवाइस **एकीकृत मेमोरी** का उपयोग करते हैं — GPU और CPU एक ही भौतिक RAM साझा करते हैं। रिपोर्ट की गई VRAM (जैसे कि Orin NX 16GB पर ~15.3GB) समर्पित GPU मेमोरी नहीं है; यह वही RAM है जिसका उपयोग ऑपरेटिंग सिस्टम और हर दूसरी प्रक्रिया कर रही है।

### स्वैप चेतावनी और सिफ़ारिशें

Jetson पर प्रोसेसिंग करने से पहले, CLI आपके इनपुट फ़ोल्डर में रॉ (RAW) इमेज की गिनती करता है (`.tif`, `.tiff`, `.raw`, `.dng` — JPG पूर्वावलोकन की गिनती नहीं की जाती), रन को आवश्यक पीक मेमोरी का अनुमान लगाता है, और यदि RAM + स्वैप अपर्याप्त होने की संभावना है तो **शुरू करने से पहले चेतावनी देता है**। चेतावनी का शीर्षक `LOW MEMORY WARNING - Jetson Detected` है, यह आपकी छवियों की संख्या प्रिंट करता है, RAM, वर्तमान स्वैप, और अनुमानित पीक, फिर सटीक `fallocate` / `chmod` / `mkswap` / `swapon` कमांड देता है जो के लिए आकार के हैं आपके प्रोजेक्ट (8GB से कभी छोटा नहीं) के लिए आकारित हैं। यह कुछ सेकंड के लिए रुकता है ताकि संदेश स्क्रॉलबैक में खो न जाए, फिर प्रसंस्करण जारी रहता है।**चेतावनी द्वारा उपयोग किए गए मेमोरी अनुमान:**

| डेबायर मोड | बेस | प्रति छवि |
| --- | --- | --- |
| मानक | ~1.5 GB | ~10 MB |
| टेक्सचर अवेयर | ~2.5 GB (मॉडल + पाइथन रनटाइम) | ~15 MB |

यह चेतावनी तब आती है जब अनुमानित पीक, रैम + स्वैप में से 1GB की सुरक्षा मार्जिन से अधिक हो जाता है, और यह केवल **फ़ाइल-समर्थित** स्वैप की ही गिनती करती है — एक zram-केवल सेटअप को अभी भी फ़्लैग किया जाएगा।

मैन्युअल रूप से स्वैप जोड़ने के लिए (उदाहरण: 8GB):

```bash
# Check current memory and swap
free -h

# Create a swap file
sudo fallocate -l 8G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile

# Make persistent across reboots
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

### OOM (आउट ऑफ मेमोरी) हैंडलिंग

प्रोसेसिंग के दौरान, Chloros जीपीयू मेमोरी की निगरानी करता है और क्रैश होने के बजाय सुचारू रूप से प्रदर्शन को कम कर देता है:

1. जब GPU मेमोरी का उपयोग **85%** से अधिक हो जाता है, तो पूर्व-सक्रिय रूप से बैच साइज़ कम कर दिए जाते हैं
2. यदि फिर भी मेमोरी की कमी की घटना होती है, तो बैच साइज़ को **आधा** कर दिया जाता है, और प्रत्येक लगातार OOM पर फिर से आधा कर दिया जाता है; प्रत्येक बाद का सफल बैच उस पेनल्टी को एक कदम पीछे ले जाता है
3. निरंतर दबाव में, पाइपलाइन `fused_gpu` से मेमोरी-कुशल `tiled_gpu` पथ पर वापस आ जाती है, और अंतिम उपाय के रूप में सीपीयू प्रोसेसिंग पर आ जाती है

क्योंकि GPU, Jetson की RAM साझा करता है, इसलिए RAM और स्वैप अभी भी एक रन को सीमित करते हैं — ऊपर दी गई स्वैप चेतावनी ही वह चेकिंग है जिस पर ध्यान देना चाहिए।

## फील्ड डिप्लॉयमेंट

### पावर संबंधी विचार

| जेटसन मॉडल     | सामान्य पावर खपत | नोट्स                   |
| ---------------- | ------------------ | ----------------------- |
| जेटसन ओरिन नैनो | 7-15W              | डीसी बैरल जैक          |
| जेटसन ओरिन एनएक्स | 10-25W             | डीसी बैरल जैक          |
| जेटसन एजीएक्स ओरिन | 15-60W             | यूएसबी-सी पीडी या बैरल जैक |

लगातार प्रोसेसिंग के लिए अपने पावर बजट की योजना बनाएँ — GPU-गहन थ्रेड 3 (प्रोसेसिंग) के दौरान पीक पावर खपत होती है।

### स्टोरेज सिफ़ारिशें

* arm64 डिप्लॉयमेंट्स के लिए **NVMe SSD** की पुरज़ोर सिफ़ारिश की जाती है
* SD कार्ड प्रोसेसिंग के लिए बहुत धीमे होते हैं — केवल बूट मीडिया के रूप में उपयोग करें
* प्रोसेस किए गए आउटपुट के लिए अपने कच्चे इमेज डेटा के आकार से 2-3 गुना की योजना बनाएँ

### हेडलेस जेसन डिप्लॉयमेंट के लिए SSH


Chloros CLI CLI का उपयोग आदर्श है:

```bash
# SSH into the Jetson
ssh user@jetson-hostname

# Process a dataset
chloros-cli process /data/datasets/flight001 --format "TIFF (32-bit, Percent)"

# Monitor export progress
chloros-cli export-status
```

### LATTICE / DAQ-E टाइम सिंक के लिए ऑलवेज-ऑन बैकएंड

यदि आपका Jetson, LATTICE कैमरों या DAQ-E लाइट सेंसरों को हेडलेस रूप से नियंत्रित करता है, तो **अपने उपयोगकर्ता के रूप में** बैकएंड systemd सेवा को सक्षम करें ताकि PTP ग्रैंडमास्टर लगातार चले और SDK स्क्रिप्ट्स को चलता हुआ बैकएंड मिल जाए (यह यूनिट डिफ़ॉल्ट रूप से इंस्टॉल है लेकिन सक्षम नहीं है):

```bash
sudo systemctl enable --now chloros-backend@$USER.service    # $USER expands to your user name
chloros-cli time-sync status
```

तब बैकएंड आपके रूप में चलता है: यह जो कैप्चर लिखता है वे आपके होते हैं, और यह आपके `chloros-cli login` का उपयोग करता है। विवरण के लिए [Linux इंस्टॉलेशन](linux-installation.md#always-on-ptp-for-headless-hosts) देखें, जिसमें रूट `chloros-backend.service` और यह भी शामिल है कि पैकेज कैसे PTP पोर्ट 319/320 को बिना रूट के बाइंड करने योग्य बनाता है।

### systemd के साथ स्वचालित प्रसंस्करण

स्वचालित प्रसंस्करण के लिए एक systemd सेवा बनाएँ:

```ini
# /etc/systemd/system/chloros-process.service
[Unit]
Description=Chloros Automated Processing
After=network.target

[Service]
Type=oneshot
User=chloros
ExecStart=/usr/bin/chloros-cli process /data/incoming --output /data/processed
StandardOutput=append:/var/log/chloros-process.log
StandardError=append:/var/log/chloros-process.log

[Install]
WantedBy=multi-user.target
```

`chloros-cli process` तब गैर-शून्य (non-zero) पर बाहर निकलता है जब कोई रन जो उत्पादों का अनुरोध करता है, कोई छवि नहीं लिखता है, इसलिए systemd की विफलता स्थिति निगरानी के लिए सार्थक है।

निर्धारित प्रसंस्करण के लिए एक systemd टाइमर के साथ पेयर करें:

```ini
# /etc/systemd/system/chloros-process.timer
[Unit]
Description=Run Chloros Processing Every Hour

[Timer]
OnCalendar=hourly
Persistent=true

[Install]
WantedBy=timers.target
```

```bash
sudo systemctl enable chloros-process.timer
sudo systemctl start chloros-process.timer
```

## उदाहरण वर्कफ़्लो

### बुनियादी जेटसन प्रसंस्करण

```bash
#!/bin/bash
# Process a drone flight dataset on Jetson
chloros-cli process /data/flights/flight_042 \
    --output /data/processed/flight_042 \
    --format "TIFF (32-bit, Percent)" \
    --indices NDVI GNDVI OSAVI
```

### जेटसन पर Python SDK


```python
from chloros_sdk import ChlorosLocal

with ChlorosLocal() as chloros:
    chloros.create_project("field_survey_042")
    chloros.import_images("/data/flights/flight_042")
    chloros.configure(
        indices=["NDVI", "GNDVI", "OSAVI"],
        export_format="TIFF (32-bit, Percent)",
        reflectance_calibration=True
    )
    chloros.process(mode="parallel")

print("Processing complete!")
```

### एकाधिक उड़ानों की बैच प्रोसेसिंग

```bash
#!/bin/bash
# Process all flight datasets in a directory
for flight in /data/flights/*/; do
    name=$(basename "$flight")
    echo "Processing $name..."
    chloros-cli process "$flight" \
        --output "/data/processed/$name" \
        --format "TIFF (32-bit, Percent)" \
        --indices NDVI OSAVI
    echo "Completed $name"
done
```

क्षेत्र और हवाई तैनाती के लिए, इन जेटसन ओरिन NX 16GB कैरियर बोर्ड विकल्पों पर विचार करें:

* **रग्ड फील्ड**: PoE GigE कैमरा कनेक्टिविटी के साथ IP67/IP69K वॉटरप्रूफ एनक्लोजर
* **न्यूनतम/बजट**: ऐड-ऑन एनक्लोजर के साथ डेवलपर किट
